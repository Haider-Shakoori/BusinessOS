- [x] Batch 5 — Authentication
  - Standard password-based authentication: login, logout, password reset (link + new password), remember me. No registration and no email verification in this batch (out of scope per roadmap).
  - Routes in `routes/auth.php`: `login` (GET/POST), `logout` (POST only), `password.request` / `password.email` / `password.reset` / `password.update` for the reset flow, and the authenticated `app.home` landing under `auth` + `auth.session`.
  - `LoginRequest` (`app/Http/Requests/Auth/LoginRequest.php`): per-IP + per-account rate limiting (5 attempts / 60s) with lockout event, generic failure message (`auth.failed`), clears limiter on success, and reports old-input ever by always redirecting to the named `login` route.
  - Form-request validation errors redirect to named routes only (never to the client-supplied Referer): `LoginRequest::getRedirectUrl()`, `PasswordResetRequest::getRedirectUrl()`, and the reset-link controller use explicit safe destinations.
  - `SafeRedirect` (`app/Support/SafeRedirect.php`): accepts only same-origin absolute URLs or local paths; rejects external hosts, protocol-relative `//host` targets, backslashes, userinfo, encoded separators, and control/whitespace characters. Used for the login `url.intended` destination and the locale-switcher redirect-back; all other redirects are hard-coded named routes.
  - Session hardening: login regenerates the session id and CSRF token; logout invalidates the session and regenerates the CSRF token while preserving only the locale preference; password reset invalidates the session and regenerates the CSRF token; a password change immediately revokes existing authenticated sessions.
  - `AuthenticatedSessionController::destroy` preserves `config('localization.session_key')` so the locale survives logout.
  - Reset-link flow uses the Laravel password broker (`Password::sendResetLink` / `Password::reset`): hashes the token in `password_reset_tokens`, never discloses account existence, and is throttled (`auth-password`, 5/min per IP).
  - `NewPasswordController::create` renders the reset page with `Referrer-Policy: no-referrer` and `Cache-Control: no-store` so the reset token never leaks via the Referer header or shared caches.
  - Password rule: required, string, min 12, max 72, confirmed, with an explicit byte-length guard (fail when the raw value exceeds 72 bytes to stay bcrypt-compatible).
  - Reset email customized in `AppServiceProvider` (`ResetPassword::toMailUsing`): localized (en/fa/ar) view `auth/emails/reset-password`, uses the configured `app.url` origin, renders the action URL via named route with `false` (path only), picks a mailer from `auth.password_mailer`, and **throws `LogicException` if the mailer transport logs the message** (log/syslog/null email transport would leak reset credentials).
  - Auth views under `resources/views/auth/`: localized login, forgot-password, reset-password, throttled (HTTP 429 view), and the post-auth home screen; dark-mode and RTL (`lang`/`dir`) aware via the Batch 4 locale foundation. Email view returns a structurally safe plain-text fallback.
  - Middleware wiring in `bootstrap/app.php`: guests redirected to `login`, authenticated users redirected to `app.home`; `SetLocale` remains in the web stack. CSRF is part of the default web middleware; disabled only within the auth test for explicit CSRF assertions.
  - Focused feature suite `tests/Feature/AuthenticationTest.php` (12 tests, 183 assertions, in-memory SQLite, real users-table migration): covers session rotation + safe intended + remember-me, generic/throttled invalid login with no password flash, guest/auth route protection, logout invalidation with locale preservation, CSRF enforcement (419), broker usage + token hashing + non-disclosure + throttling, reset confirmation + credential rotation + token consumption, expired-token rejection, session revocation on password change, open-redirect resistance, localized views/validation in en/fa/ar, and localized reset mail on the configured origin that forbids logging transports.

- Batch 3 decisions: CSS-first sidebar collapse via `@custom-variant sidebar-collapsed` (256px/64px widths and content padding driven by that variant) with a pre-paint inline script so the shell never flashes the wrong width; collapse preference mirrored to `<html>` and persisted in localStorage (`bos-sidebar-collapsed`); navigation data seam `App\Support\Navigation` (label/icon/route/href items) is a placeholder swap point for the Batch 8 Module Registry — the shell renders only that item contract; mobile navigation reuses the Batch 2 `bos:open-drawer` + `drawerPanel` contract instead of a parallel mechanism.
- Batch 4 decisions: session-based locale persistence (no database, no auth dependency) with `SetLocale` middleware reading from `session('locale')` and validating against `config('localization.supported')`; text direction determined by locale config (`en`=ltr, `fa`/`ar`=rtl) and rendered as `dir` attribute on `<html>`; translation keys follow `domain.key` convention (e.g., `common.dashboard`, `navigation.customers`); `x-app.locale-switcher` uses the same `x-ui.dropdown` pattern as the user menu; locale switching does NOT prefix URLs — session-only for now, URL prefix architecture explicitly deferred to Batch 26 completion.
- Batch 5 decisions: authentication redirects never trust client-supplied Referer/intended data — validation errors and form requests redirect to hard-coded named routes, the post-login destination uses `App\Support\SafeRedirect::path()` (same-origin absolute URLs or local paths only), and the locale redirect-back uses the same guard. Reset tokens are protected with `Referrer-Policy: no-referrer` + `Cache-Control: no-store` on the reset page and a wall against logging mail transports for reset mail. Pending subsequent batches: registration, email verification, and multi-factor authentication are explicitly out of scope and not implemented.
- Batch 7 decisions: permissions are global rows (never business-scoped) keyed by `entity.action`; roles are business-owned and strictly scoped by `business_id` FK + `(business_id, slug)` uniqueness, and the `Role` model deliberately does NOT carry the tenant `business` global scope (authorization metadata is only reachable through business/membership relations, keeping provisioning/audit queries context-neutral; the membership pivot + `hasPermission`'s business filter are the enforcement boundary); roles are assigned to memberships (never users) through the `business_membership_role` pivot (preferred over a `role_id` column on `business_memberships`, so a user can hold different roles per business); authorization is evaluated by a single scoped service (`MembershipAuthorization`) under the current business, and the whole pipeline is wired into `Gate::before` so Blade uses `@can('entity.action')` natively; middleware (`permission:...`) and `@can` share the same key space but differ in trust — a hidden menu is a convention, the middleware/guard is the security boundary; only registered permission keys are interceptable (free-form abilities fall through to `null`, preserving future Policy composition); no Spatie/perm packages, no super-admin, no system-wide roles in this batch.
- Batch 8 decisions: modules are code-backed in `config/modules.php` (stable keys + metadata; never a DB master module list) with per-business enablement ONLY in `business_modules`; default provisioning is idempotent and runs inside the onboarding transaction (dashboard + settings only — customers etc. are opt-in); module enablement is strictly separate from authorization — `module:key` checks availability only (guest → login, unregistered/disabled → 403) and composes with the standalone `permission:key` middleware, never replacing it; navigation filters at the data source (enabled AND permission) behind the same `Navigation` shell contract, with `#` as the safe inert destination; the permission catalogue gained exactly one key (`customers.view`, owner+admin only) purely to support the mandate module-vs-permission scenario; no module-toggle UI/routes, no Batch 9 settings, no packages.
- Batch 6 decisions: business context is a scoped container service (per-request lifecycle restored via the prepended `ForgetScopedInstances` middleware, since Laravel 12.69 removed the framework middleware of that name); resolution is deterministic (stored selection validated against membership, else smallest accessible id) and persisted to the session key `config('business.context.session_key')` = `current_business`; the tenancy scoping convention is a named global scope `business` on tenant-owned models via `BelongsToBusiness` that is a deliberate no-op when no current business exists (never hides full tables outside an authenticated UI request); business ownership/membership is the only isolation boundary in this batch — role/permission authorizations are Batch 7; business creation is transactional and never accepts ownership hints from the request; `businesses` stays minimal (name only) with slug/status deferred until later batches require them; no tenancy packages (e.g., `stancl/tenancy`) and no permission packages installed.
